Factory Inventory Management System

A demo operations dashboard: a Vue 3 single-page app backed by a FastAPI service, which serves mock data from JSON files held in memory. There is no database.

System architecture

Three tiers. The browser calls the API directly across origins, with no Vite proxy, which is why the backend enables CORS.

Frontend: Vue 3 single-page app

client/ · localhost:3000 (Vite)

App shell

App.vue, with the navigation, global FilterBar, language switcher, profile menu and tasks modal. Also holds the global styles.

Views (vue-router)

Dashboard, Inventory, Orders, Spending, Demand, Restocking and Reports, plus detail modals in components/.

Composables (shared state)

useFilters for the filter singleton, useI18n for locale and currency, useAuth for the mock user.

API client

api.js wraps axios and builds query strings. Reports is the exception: it calls axios directly.

HTTP + JSON (axios requests, with filter query params on reads)

Backend: FastAPI service

server/ · localhost:8001 (uvicorn)

Routes

main.py defines every endpoint in one module, including the summary and report aggregations.

Filter helpers

apply_filters for warehouse, category and status. filter_by_month for months and quarters.

Pydantic models

Validate responses for the inventory, orders, demand, backlog and restocking endpoints.

Data loader

mock_data.py reads every JSON file once on import and exposes the results as module-level lists.

Read once at startup, then served from memory until restart

Data flow

What happens when a user changes a filter on the Orders page. Most data in the app follows this path.

  1. The user picks a filter. FilterBar updates the shared refs. client/src/components/FilterBar.vue
  2. Every mounted view sees the same state. The refs live at module level, so useFilters() returns a singleton, and the view's watch fires. client/src/composables/useFilters.js
  3. UI state becomes API params. getCurrentFilters() maps location to warehouse and period to month. client/src/composables/useFilters.js
  4. The API client sends the request. It omits any filter set to all and calls axios.get. client/src/api.js
  5. FastAPI filters in memory. The route runs apply_filters and filter_by_month over the loaded lists, without changing them. server/main.py
  6. The response is validated and returned. The route's response_model shapes the JSON. server/main.py
  7. The view re-renders. The result goes into a ref, and computed properties derive the KPIs, tables and charts. client/src/views/Orders.vue

Things to know

Found while tracing the code, including places where the frontend and backend have drifted apart.

The tasks API does not exist on the backend

App.vue calls /api/tasks on load and when adding tasks, but main.py has no such route. The errors are only logged to the console, so the modal shows just the mock tasks from useAuth, and new tasks are never added.

Purchase orders are only partly built

api.js has two purchase order methods with no callers and no backend routes. main.py defines the models and reads purchase_orders.json, but that file is empty, so has_purchase_order is always false.

Backlog.vue is not reachable

The view exists, but main.js has no route for it. Backlog data currently appears only on the Dashboard.

Some filter controls have no effect

The filter bar stays visible on Reports and Restocking, which ignore it. On the Dashboard, total_backlog_items always counts the full backlog, whatever the filters.

Nothing persists, and there is no real authentication

The only write route adds restocking orders to an in-memory list, which is lost on restart. useAuth returns a hard-coded user. Only the language choice is saved across sessions, in localStorage.

Local development only

The API URL is hard-coded in api.js and Reports.vue. The backend allows all CORS origins and binds to 0.0.0.0, so it needs tightening before any deployment.
